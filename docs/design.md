# Office Inventory — agreed scope and implementation defaults

The user wants a new, simple inventory system for one office, used on one computer at a time. It tracks individual equipment assigned to employees. A Save Inventory file is carried to another computer; Load Inventory makes that installation match the saved snapshot. This is a separate application from the existing inventory_Sys.

## First version

- One searchable equipment list with employee and condition filters, totals, CSV export, and printing.
- Equipment records: property number, equipment name, category, brand, model, serial number, assigned employee, location, condition, and notes. Only property number and name are required. Unassigned equipment is allowed when returned or awaiting assignment.
- Employee list: name and optional position. Equipment assignment is edited directly on the item; every saved change records readable history. Archive/restore equipment instead of deleting its history.
- Three main views: Equipment, Employees, Save & Load. Office name can be edited in Save & Load.
- Save Inventory downloads one versioned .inventory JSON file containing settings, employees, equipment, and history. Show its date/time and counts before loading. Loading replaces all current records in one transaction and first writes a complete recovery save to backups/. Malformed or incompatible saves do not change data.
- A local SQLite file stores records between sessions. The app binds only to 127.0.0.1. No login is included for this single-computer version; access follows the Windows account/session.
- Double-click Start Inventory.bat to open the browser with the app running in the background; Stop Inventory.bat closes this app. Prefer port 3210, falling back to an OS-assigned free loopback port if the preferred port is occupied or inaccessible. Both launchers discover the actual port from this folder's runtime state and verify instance ownership. Startup reuses this app and never stops other processes.
- Provide a portable Windows x64 folder, bundling the locally verified Node.js 24.17 runtime and its license if available. Otherwise disclose the Node prerequisite. No npm install, Docker, or internet service is needed for daily use.

## Boundaries

No quantity stock, multiple-office hierarchy, approval workflows, custom permission builder, cloud syncing, account management, file attachments, or automatic import from the old system in this release. Save files represent the latest saved point; the user makes a new save before moving between computers. The app always starts empty and contains no invented employee or equipment records.

## Implementation interfaces

Store factory: createStore({ dataDir }) from src/store.mjs. Methods are synchronous: getState(), saveEmployee(input, id?), saveEquipment(input, id?), getHistory(equipmentId), exportSnapshot(), previewSnapshot(snapshot), restoreSnapshot(snapshot), updateSettings({ officeName }), close(). Validation errors carry numeric status 400/404/409 and a readable message.

State: { settings: { officeName }, employees: Employee[], equipment: Equipment[] }. Employee: { id, name, position, active, createdAt, updatedAt }. Equipment: { id, propertyNumber, name, category, brand, model, serialNumber, employeeId: string|null, location, condition, notes, archived, createdAt, updatedAt }. Conditions exactly: Good, Needs repair, Unserviceable. History: { id, equipmentId, at, action, summary, before: Equipment|null, after: Equipment }. IDs are UUIDs generated by the store.

Snapshot: { format: 'office-inventory', version: 1, savedAt, settings, employees, equipment, history }. Preview: { savedAt, officeName, equipmentCount, employeeCount, historyCount }. Restore returns { summary: Preview, recoveryFile }.

HTTP JSON: GET /api/state; POST /api/employees; PUT /api/employees/:id; POST /api/equipment; PUT /api/equipment/:id; GET /api/equipment/:id/history; PUT /api/settings; GET /api/backups/download (file response); POST /api/backups/preview (bare snapshot); POST /api/backups/restore ({ snapshot, confirm: true }). Mutations require Content-Type application/json and X-Inventory-Request: 1. Success bodies are store method results; failures { error: string }. Export CSV and print are frontend actions on the filtered inventory.

## Acceptance

Create employee and equipment, assign and transfer equipment, see history, edit/archive/restore, restart and retain data; export and load a save into a second empty data directory with identical records/history; reject corrupt, incompatible, duplicate-ID/property-number, or broken-reference saves without data loss; recover the prior state from the automatic recovery save; startup reuses its own app and stops only its instance; check layout and keyboard forms in a browser.
